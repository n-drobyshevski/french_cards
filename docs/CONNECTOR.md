# Claude connector («Карточки» in the Claude apps)

The app serves a remote MCP server at `/api/mcp/<MCP_SECRET>`. Added once as a custom connector on claude.ai, it works in Claude on the web, desktop and mobile, and in Claude Code signed in with the same account. Claude can then search, add, edit, move, delete and restore words, fill in custom fields («Свои поля»), undo moves, create themes, read today's study numbers and the «Прогресс» history, write exercise sets («Упражнения») for the app to play, and play a set right in the chat (an MCP App player, or the same player as an HTML artifact), also as a timed «Мини-TCF». New words and levels Claude proposes can be checked on a card in the chat before they are written («Новые слова», «Уровни слов»: a second MCP App). Grading reviews stays in the app.

An optional skill (`claude/skills/kartochki/`) teaches Claude the card conventions: the slang-level rubric, verlan, translation and example style, when to ask before changing anything, and recipes. The connector works without it.

## How it works

- **Transport:** stateless Streamable HTTP via `mcp-handler@2` and `@modelcontextprotocol/server@2` (`app/api/mcp/[key]/route.ts`). Each request builds a fresh server; nothing is kept between requests, and no Redis is needed.
- **Auth:** none at the MCP level ("authless" connector). The secret path segment is the only credential.
  - The route compares SHA-256 hashes of the path key and `MCP_SECRET` in constant time.
  - A wrong key, a missing or short (< 32 characters) secret, a missing `MCP_USER_ID`, a missing `SUPABASE_SECRET_KEY` or one that is not a secret key (a publishable key is refused), or local-only mode all answer a plain `404`, whatever the HTTP method.
  - Responses carry `Cache-Control: no-store`. The app never logs the path.
  - `proxy.ts` does not run on `/api/mcp/*`, so the canonical-host redirect can't turn a POST into a 308.
- **Data:** there is no user session, so the server uses the Supabase **secret key** (it bypasses RLS) for the one `MCP_USER_ID`.
  - All access goes through `lib/mcp/repo.ts`, which adds `user_id = MCP_USER_ID` to every query and sets it on every written row.
  - The `kartochki_stamp_row` trigger still runs: it stamps `synced_at`, so devices pull Claude's changes on their next sync (on open, on focus, or within about 5 minutes while the app is visible).
  - Writes follow the app's rules (`lib/mcp/tools.ts`): new words get both review cards (written before the word) and `source = "chat"` («из чата» in the word sheet); rewrites stamp `updated_at` past the stored value; nothing is hard-deleted.
  - Rewrites of a word are compare-and-set: the row is written only if its `updated_at` is still the one read just before. If the phone synced a change, or another call changed the word, in between, Claude gets a `conflict` instead of overwriting it.
  - Migration `0005_connector_grants.sql` grants `service_role` the table rights the connector needs, so it does not depend on the project's default privileges. Migration `0006_custom_fields.sql` adds `words.custom_fields` and the `field_defs` table, with `select` for `service_role`; `0007_connector_field_writes.sql` adds `insert, update` so the connector can manage the shared fields (deletes stay soft). Without 0006, `search_words`, `update_word`, `list_fields` and `add_words` with `custom_fields` fail with a database error.
- **No subscriptions:** the server's tool list never changes, so it refuses `subscriptions/listen` streams (`maxSubscriptions: 0`) instead of holding a function open.
- **Rate limit:** write tools take a token from the in-memory `mcp` bucket (`lib/ai/rate-limit.ts`, 20 in a burst, then one per 3 s). An exhausted bucket gives an `isError` tool result; `initialize` and `tools/list` are never limited.
- **«Сегодня»:** `study_summary` computes the 04:00-to-04:00 study day in `MCP_TIMEZONE` (`lib/mcp/study-day.ts`) and plans it with `planDay` (`lib/core/plan.ts`) and the synced «План повторения» (`user_prefs` `study_plan`), as the app does. Without a saved plan it uses the default migrated from 15 cards a day (8 words); a device with another «Новых в день» saves its migrated plan after a sync. The one-day «Всё равно добавить новые» is device-local and not seen here.
- **«Прогресс»:** `study_summary` `history_days` (1–365) adds `history`, see below.
- **«План и прогресс»:** `study_summary` always returns `plan_fit`: the saved plan against her last study days, and the one change worth offering, see below.

Themes can be named by id, slug, Russian name, or `inbox`.

### Custom fields («Свои поля»)

The shared definitions are edited in the app (Settings → «Свои поля»); the connector only reads them (`repo.fieldDefs()`). Claude addresses fields by name:

- **Input** (`add_words` per word, `update_word` in `patch`): `custom_fields: { "<name>": "<value>" | null }`. A name that matches a live shared field (any case) sets that field (`field_id` = the definition's id, label = its current name); any other name creates a one-off field on that word (`field_id: null`). `null` or an empty value clears a field. `update_word` changes only the named fields and keeps the rest; clears are applied first. Names are at most 40 characters and values at most 300 (longer input is refused, like other fields); whitespace is collapsed. A word holds at most 12 fields; a call that would go past that is refused before anything is written.
- **Output:** words in `search_words`, `update_word` and `add_words` results carry `custom_fields: { "<name>": "<value>" }` only when they have any. Shared fields come first under the definition's current name; one-off fields and values of deleted definitions follow under their stored label. When a call created one-off fields, the result lists them in `new_one_off_fields` (per added word in `add_words`) with a `fields_note`, so Claude can tell a misspelt shared name.

### «Уровень языка» (CEFR A1…C2)
- **What the app shows:** a level per word, resolved by `lib/core/level.ts` (shared by the app and the connector): a level stored on the word (`words.cefr` + `words.cefr_source`: `user`, `chat` or `ai`), else an estimate computed on the fly and never stored: FLELex-Beacco on the lemma and part of speech, then an exact FLELex CRF expression, then the Lexique frequency rank (≤800 A1, ≤2000 A2, ≤4000 B1, ≤7000 B2, ≤12000 C1, else C2); argot, vulgar words and verlan get no estimate. Nothing found = «без уровня». The app shows «≈B1» for every level the user did not pick. The level only orders new words («По уровню языка», the plan's default) and filters the library; it never gates anything.
- **Output:** every word in `search_words`, `update_word`, `add_words` and `set_word_levels` results carries `level` (null = none) and, with a level, `level_source`: `user`, `chat`, `ai`, `flelex` or `freq`. The server bundles `public/lexique/fr-cefr.json` and `fr-lemmas.json` (`lib/mcp/levels.ts`), as it does `fr-conj.json`, so its estimates match the device's.
- **Input:** `cefr` on `add_words` (per word; optional, saved as `chat`) and on `update_word` (`null` clears the stored level; the same level as stored keeps its source, so a user's level stays the user's). `set_word_levels` sets up to 100 at once: `items[].cefr` (null clears), `overwrite_user` (default false: words with a `user` level are listed in `skipped_user` and left alone). Words that changed meanwhile come back in `conflicts`; `undo` is `{tool: "set_word_levels", items: [{word_id, cefr, source, expect}], overwrite_user}`, which puts each word's level and source back exactly (`items[].source` exists only for that and is refused without `expect`). `expect` is the level the call wrote: a word whose level changed since (e.g. the user picked one in the app) is left alone and listed in `changed_since`. `overwrite_user` is true only when the call itself wrote a user's level (undoing an undo).
- **Filling the gaps:** `search_words` with `level: "none"`, then `propose_levels` in batches of 15 rated against words of known level: the «Уровни слов» card saves them with `set_word_levels` on the user's tap, and its «Следующие 15 ›» asks Claude for the next batch. Where no card shows: list the words with the proposed levels, wait for the OK, then `set_word_levels` in batches of 10–15. The app's own «Определить уровень языка» (library) does the same through `/api/ai/enrich` and saves `ai`.
- **Storage:** `words.cefr` (text, check A1…C2) and `words.cefr_source` (text, check user / chat / ai), migration `0014_word_level.sql`, synced like the other word columns.

### Origin and conjugation («Контекст»)
- **Input** (`add_words` per word, `update_word` in `patch`): `origin` — one Russian line, at most 200 characters («верлан от lourd», «от volonté „воля“ + -aire»); `null` clears it. `conjugation` — verbs only (`pos` verb, or expression in `update_word`): `{ auxiliary: "avoir"|"être", remark?, present, passe_compose, imparfait, futur }`, each tense exactly six forms je → ils with pronouns; `null` clears it, and the app goes back to the one it builds from Lexique. A conjugation on another part of speech is refused by `update_word` and dropped by `add_words`.
- **Output:** words carry `origin` when they have one; verbs carry the saved `conjugation` (same flat shape) or `conjugation_builtin` (true when the app conjugates the verb itself from Lexique, false when it cannot, so Claude knows which ones to fill).
- **Storage:** `words.origin` (text) and `words.conjugation` (jsonb, `{auxiliary, remark, tenses: {present…}}`), migration `0008_word_origin_conjugation.sql`, synced like the other word columns. The app shows them in «Контекст» (they win over the lookup's origin line and the built-in conjugation) and the origin under the translation in the word card.

### «На паузе»
- `update_word` `patch.muted`: `true` keeps the word in the library but takes it out of every review and practice round (the review card's mute button does the same); `false` brings it back with its progress.
- **Output:** such words carry `muted: true`; their `due_today` is false and `study_summary` leaves them out of the due and new counts.
- **Storage:** `words.muted` (boolean, default false), migration `0009_word_muted.sql`, synced like the other word columns.
- **A whole theme:** `update_folder` `muted: true` pauses every word of the theme (`false` brings them back with their progress). `list_folders` marks it `muted: true` and gives every theme a `new` count (words never reviewed); `search_words` marks its words `theme_muted: true`; `study_summary` lists `muted_themes` and leaves their words out of the due and new counts. Storage: `folders.muted`, migration `0010_folder_muted.sql`.
- **Proposals:** the server instructions ask Claude to suggest pausing themes that look like later steps of a sequence (levels, lessons, chapters) or that the user said can wait, when many themes still hold new words — naming them and waiting for the OK, never pausing on its own.

### «Прогресс» (`study_summary` `history_days`)
The app saves the library's end-of-day numbers once per finished study day in the synced `progress_days` table (`lib/progress.ts` `ensureProgressDays`, migration `0016_progress_days.sql`, which grants `service_role` `select`); the connector only reads it (`repo.progressDays()`), and never writes or replays days. With `history_days: N`, `study_summary` adds:
- `from` / `to`: the range, today − N + 1 to today (study days in `MCP_TIMEZONE`).
- `columns` + `days`: the stored rows of the range as arrays, ascending — `day, known («знаю»), learning («учу»), fresh («новых»), paused («на паузе»), difficult («трудных», part of learning), memorized («помню ≈», 1 decimal), reviews, again, new_introduced, added, source (live | replay)`. Days without a row are missing; today is never stored.
- `today`: the same counts now (`countsFromStates`).
- `active_days` (in the range) and `streak: { current, best }` (`streaks`): a day is active with a live `review_log` row or a finished exercise run; days before the logs read (the 1st of `from`'s month) count from their stored row's `reviews`, as the app's calendar does.
- `retention`: «Верно», true retention (the first live log of each card per study day, when it came as a review card; passed = rating > 1) for the range and per calendar month from `from`'s month (`retentionOf`), with `target` 0.9 (`TARGET_RETENTION`); rates have 2 decimals, months without counted reviews are left out.

The rules are the shared pure ones in `lib/core/progress.ts`; their day keys follow the device clock, so the connector keys every log, run and row by `MCP_TIMEZONE` instead (`lib/mcp/study-day.ts` `studyDayKey`, `lib/mcp/history.ts`). Without migration 0016 `study_summary` fails with a database error (it reads the table for `plan_fit` too; the app's sync needs 0016 anyway).

### «План и прогресс» (`study_summary` `plan_fit`)
Always there, whatever `history_days` or `new_per_day` say: `lib/mcp/plan-fit.ts` runs the app's own `planFit` (`lib/core/plan-fit.ts`, the numbers Settings → «План повторения» shows) on the saved plan, with every day keyed by `MCP_TIMEZONE`. It reads the live logs of the last 28 study days (56 once the stored rows reach back 60 days, for the observed reviews per new word), `progress_days` (the kept day plans in `plan`, migration 0017, and the first study day), `user_prefs` `plan_day` (today's and yesterday's plan before its row is written), `plan_hint` (read only: «Не сейчас» in the app) and today's `planDay`. Snake_case, `null` for what is unknown (never NaN):
- `window_days` (14), `active_days` (study days in the window: the last ≤ 14 within 3 weeks; days without study are not data), `plan_since` (since when the current ceiling and cap hold: the `study_plan` row's `updated_at`, moved back over kept days with the same plan).
- `new_words`: `plan` (the ceiling), `unit` (`words`, or `cards` with `ru_fr` "together"), `typical` (median a study day), `max`, `full_days` (days that took all of them) of `plan_days` (study days under the current plan), `held_days` `{load, accuracy, backlog, known}` (days the plan held new words back, by reason; null when no day's plan was kept).
- `reviews`: `cap`, `typical` (median interday answers, what the cap counts), `all_answers_typical` (every answer), `max`, `forecast_7d`, `backlog_days`, `cap_hit_days`.
- `retention`: `rate` (2 decimals), `target` 0.9, `answers`, over 28 days.
- `fit`: `warming_up` (not enough data: under 5 days since the first study day or under 5 study days (shortened from 14 / 7 on 2026-10-25); a plan changed under 7 days ago holds back only `suggestion`), `fits`, `room` (the whole plan on most days, low load, retention fine) or `heavy` (backlog with a loaded week, low retention or a heavy forecast).
- `suggestion`: null, or `{kind: raise_new | lower_new, new_words, or_review_cap?, forecast_30d: {now, then: [lo, hi]}, why, confidence}`; `confidence: "low"` (5–6 study days) only reaches the connector. Studying less than the plan allows never gives a suggestion, and the cap is never suggested lower.
- `dismissed_until`: the day «Не сейчас» stops hiding the suggestion.

No `missed_days`, `deficit` or `compliance`. Claude may propose the suggestion once per conversation when the talk is about the plan, pace, load or progress, never as an opener, and changes the plan only after the OK (`update_study_plan`). Without migration 0017 the rows carry no `plan`: `held_days` is null and the rest is the same.

### Упражнения
Claude writes Duolingo-style question sets through the connector; the app plays them offline from its synced copy and never asks the API for them. Exercises never write `review_state` or `review_log`.
- **Storage:** `exercise_sets` and `exercise_runs`, migration `0011_exercises.sql`, synced like the other tables. The connector writes a set's content once (`create_exercise_set`, or a chat set with its first saved round) and later only its `deleted_at` (delete / restore); the app only sets `deleted_at` too. Runs are written by the device that plays them (one row per playthrough, upserted after each answer); the one exception is a round played in the chat, which `save_exercise_result` writes once under an `xr-` id no device uses, so last-write-wins never fights over a row. `service_role` has `select, insert, update` on `exercise_sets` and, since `0019_connector_exercise_runs.sql`, on `exercise_runs` (`'exercise_runs'` is in `WritableTable`, `lib/mcp/repo.ts`).
- **Input** (`create_exercise_set`): `{ client_ref ≤40, title ≤60, topic?, folders?, items 6–20, new_words? ≤8 }`. `items`, `new_words` and `folders` may also come as JSON strings. `play_exercises`, `exercise_artifact` and `save_exercise_result` share the schema and the build-and-check step (`buildSet`), with `set_id` instead of the fields for a saved set. The item contract is documented on `ExerciseItem` in `lib/types.ts`; the rules live in `lib/core/exercises.ts` (shared with the app). A `reading` item («текст», TCF compréhension écrite) carries `passage` (French, `PASSAGE_MIN`–`PASSAGE_MAX` = 40–900 characters, line breaks kept; the descriptions ask for 300–700), `passage_label` (≤ 20, letters only, stored upper-cased: ANNONCE, MESSAGE, ARTICLE, AVIS…), `prompt` (the French question), `answer` and 3 French `distractors`, and an optional `word_id` (never `new_ref`). Any item may carry `level` (A1…C2, kept only when valid); the app shows it as «≈B1» on the card, the exam scores by it. No migration: both live in the `items` jsonb.
- **What the server does:** the id is `x-` + the first 24 hex digits of `sha256(client_ref)`, so a retry hits the same row: a replay of a live set answers `already_saved: true` and writes nothing; a `client_ref` whose set was deleted is refused with a pointer to `restore_exercise_set`. The items are renumbered `q1…qN` (ids Claude sends are ignored). `completeSet` copies each word into the set (it plays without the library), writes the `choice`/meaning prompt and answer and the `pairs` tiles, and for `conjugate` (`tense` + `person`) the infinitive prompt, the `sentence` «tu [[as kiffé]]», the answer and, when left out, 3 distractors from the verb's conjugation (the word's saved one, else the one built from Lexique; `conjugateDistractors`: the other auxiliary in the passé composé, then the same person in the other tenses, then other persons); `validateSet` then refuses the whole set, listing every error by path (`items[7].word_id: no such word …`): a `register` item (dropped 2026-10-25: «register items are no longer used; use choice/cloze/pairs/conjugate»), unknown, deleted or paused words, an unresolved `new_ref`, a new word that is already saved («use word_id …»), anything but 3 distinct distractors different from the answer, a cloze span that is not the answer, bad pairs, a `conjugate` item with a bad tense or person or about a verb with no conjugation, more than 10 `conjugate` items; a `reading` item without a French passage of 40–900 characters or a French question, with options that are not 3 distinct French distractors, with a bad label, an unknown `word_id`, or any `new_ref`. Themes are resolved like everywhere else (id, slug, name, `inbox`). The row is one upsert, so a failure saves nothing; the result is a summary (`{ id, title, count, by_type, new_words }`, `warnings`, `undo`), never the set.
- **Warnings** (`warningsFor`, saved anyway): fewer than 3 types (not for a set that is mostly `conjugate` or at least half `reading`), the answer is the longest option in over 60 % of items (reading included), an answer shows in a stem (for a reading item only its own question is checked: its answer is meant to be found in the passage), the same word in two consecutive items, over 30 % new words.
- **«Чаще в упражнениях»:** the user's choice in Settings → «Упражнения» of which words sets should favour (`normal` off, `difficult` = a card `cardStatus` difficult, `due` = a card due today, `both`) and how much of a set (`some` ≥25 %, `half` ≥50 %, `most` ≥80 %; `lib/core/exercise-focus.ts`). Stored in the synced `user_prefs` table (row `exercise_focus`, `value` jsonb), migration `0012_user_prefs.sql`; `service_role` has `select` only (`repo.userPrefs()`), the app writes it. `exercise_material` reads it (an input `focus: {target, share?}` overrides it for one request, the saved share kept when none is given), ranks the in-scope focus words first (then the weakness order), marks them `focus: true` and returns `focus: { target, share, from: "settings"|"request", min_items_for_12, available, note }`, or `{ target: "normal" }` when off. `create_exercise_set` adds the warning `focus_share` when the saved focus (never an override) asks for more focus-word questions than the set has: an item counts when its `word_id` is a focus word, a `pairs` item when at least half its words are; the expectation is `focusMinItems(focus, items)` capped at the number of focus words in the set's themes (every unpaused theme when it names none).
- **«Уровень набора»** (`levels`, migration `0018_exercise_level.sql`: `exercise_sets.levels` text[] of A1…C2, `{}` for none, `level_auto` boolean): the CEFR levels a set's questions are written at, one or several. The app's request adds them after the size («Сделай в Карточках 12 вопросов уровня B1–B2 по …», desktop «…, 12 вопросов, уровень B1–B2, …»; neighbours as a range, `levelsText`; «Авто» copies nothing). `exercise_material` `levels` returns `level: { targets, from: "request", guide, note }` (several: spread the questions about evenly, easier first); without them `from: "auto"`, `targets` = [the median level of the in-scope neutral words] (`autoLevelOf` in `lib/core/exercises.ts`: slang and verlan words aside, folded into A2…C1; B1 when none has one) and `words_level`. `guide` (`LEVEL_GUIDE` in `lib/mcp/tools.ts`, one entry per target) says what a level asks of sentences (length, tenses, topics), distractors (how close), the recognition / production mix and new words; the levels never change which library words are asked. `create_exercise_set` stores `levels` and `level_auto`, and warns `level_words` (`levelWarnings`) for words in cloze sentences, French options and `new_words` two levels or more above the highest level by the app's dictionary (`lemmaLevel` in `lib/mcp/levels.ts`: only words written as a Lexique lemma, so inflected forms are skipped, never misread; the asked words, the gap and capitalised names aside). `list_exercise_sets` and the result's `set` show `levels` (and `level_auto: true`); the app shows them on the tile («12 ВОПРОСОВ · B1–B2», «≈B1» from «Авто») and in the set's menu.
- **Only difficult / due words** (`scope`, migration `0013_exercise_scope.sql`: `exercise_sets.scope` text, null or `difficult` / `due` / `both`): a set made only of the user's difficult words, the words due today, or both, from every theme — the app's «Откуда слова», quick tiles, library ledger and review done screen copy «Сделай упражнение в Карточках по трудным словам из всех тем, 12 вопросов.» (`buildRequestText` with `scope`; the phone request sheet and empty state copy the one-sentence form «Сделай в Карточках 12 вопросов по трудным словам из всех тем.», `buildRequestSentence`). `exercise_material` `only` returns just those words (live and not paused, even in a theme named in `folders`, which still narrows them; `topic` and `focus` are left out) with `scope: { folders, days, only, available, suggested_items, note }`: `suggested_items` = min(12, max(6, available × 3)), 0 when there are none, and the note says to use only these words, each in 2–3 types, no new words, or, with none, to tell the user there is nothing to drill. `create_exercise_set` stores `scope`, refuses non-empty `new_words` with it (path `new_words`), skips `focus_share` and warns `scope_words` for items whose words are off scope (the same difficult / due flags). `list_exercise_sets` shows `scope` (null for an ordinary set or a row from before 0013); the app counts the available words with `useScopeCounts` (`lib/exercises.ts`, like the library ledger).
- **Closing the loop:** `exercise_material` and `list_exercise_sets` read the runs (`repo.exerciseRunsSince`, by `started_at`), so Claude can build «работа над ошибками» from the misses and the wrong options picked.
- **No more `register` items** (dropped 2026-10-25: the user picked нейтр. / fam. / arg. / vulg. for a word): the input schema and `validateSet` refuse a new one, and old stored sets still load (`EXERCISE_ITEM_TYPES` keeps the type). Their register items are skipped wherever a set is played, like an unknown type (`PLAYED_ITEM_TYPES`, `runItems`: not in the queue, the score, the tile counts or «Повторить ошибки»); `play_exercises` by `set_id` leaves them out and says how many it skipped, and `exercise_material` doesn't take a miss on one as a confusion.

### Упражнения в чате (MCP App)

When the user asks for exercises in the chat («в чате», «здесь», «прямо тут»), Claude calls `play_exercises` instead of `create_exercise_set`, and the host shows a player right in the chat: an MCP App (spec `io.modelcontextprotocol/ui`, stable 2026-01-26). It plays by the app's rules and looks like the phone player (SPEC.md «Упражнения», E3 B / E4 B): the question card on a small deck, the 2×2 options, the ВЕРНО / НЕВЕРНО stamp, «Дальше» after every answer, «Не знаю», a miss requeued up to 3 times, intro cards for new words, the pairs board, conjugation, reading texts (the passage as a quoted block with its mono label, then the French question), and the done card «ИТОГ НАБОРА» with the cells and «3 из 5 с первого раза». Old register items and unknown types are skipped; a missed reading question with no word shows under «Вопросы к текстам» and goes into «Обсудить ошибки».

- **The contract** is `lib/core/chat-player.ts`: `CHAT_PLAYER_URI`, `MCP_APP_MIME` (`text/html;profile=mcp-app`), `SAVE_RESULT_TOOL`, `ChatPlayerSet` (the tool result's `structuredContent`, or the artifact's embedded JSON; `mode` `practice` / `exam`, `time_limit_s`), `EXAM_SECONDS_PER_ITEM`, `CHAT_ITEM_TYPES`, `ChatRunResult`, `saveArguments`, `runLine` / `parseRunLine` (`RUN_LINE_PREFIX` = `KARTOCHKI_RUN `) and `fillArtifact`.
- **The page** is the `ui://kartochki/exercise-player.html` resource (`server.registerResource`, `exercise_player`), returning `CHAT_PLAYER_HTML` from the generated `lib/mcp/chat-player-html.ts`. It is self-contained: one inline script and stylesheet, system font stacks with the app's colour tokens (light and dark, following the host's theme), no network, so it declares no CSP domains. It deliberately sets no `_meta.ui.domain`: a host derives that sandbox origin from the server URL, and ours carries the secret. The player talks to the host over the spec's postMessage bridge (`chat-player/bridge.ts`: `ui/initialize`, the tool input and result notifications, size changes, `tools/call`, `ui/message`, `ui/update-model-context`). `play_exercises` carries `_meta.ui.resourceUri` (plus the drafts' flat `ui/resourceUri` key for older hosts).
- **Nothing is written while playing.** At the end the player puts a one-line summary into the model's context (score, missed words, saved or not); «Обсудить ошибки» sends a user message listing the misses. «Сохранить в Карточки» calls `save_exercise_result` with `saveArguments(set, run)`. The call goes through the host, so the tool's permission applies: at «Needs approval» the host shows its Allow prompt after the tap (a second yes); an error or a refusal is shown on the button's hint, and the round stays in the page to try again. After a «Повторить ошибки» round the buttons keep the newest whole round (the result format has no item list).
- **Fallback, the artifact:** hosts that render no MCP Apps (Claude Code), a user who doesn't see the player, or a page to keep get `exercise_artifact`: the same bundle built as `CHAT_PLAYER_ARTIFACT`, the set filled into `ARTIFACT_SET_SLOT` by `fillArtifact` (`<` escaped, the set's title as `<title>`), which Claude publishes verbatim as an HTML artifact. It has no bridge: its done screen copies `runLine(result)` («Скопировать результат»), and Claude saves the pasted line with `save_exercise_result` `run_line` only after asking. Claude rebuilds an exercise artifact the user already has only when asked to change it (more questions, another topic), keeping its title and topic.
- **Host support:** the player needs a host that renders MCP Apps (Claude on the web and in the desktop app). A host that doesn't (Claude Code; check the mobile apps before relying on them) shows only the tool call: the tool description, the result text and the server instructions all tell Claude to switch to `exercise_artifact` then. Outside a frame the page only says «Плеер открывается в чате с Claude.». The MCP App mode has been checked against a test host page, not yet in a real Claude chat.
- **Build:** `npm run build:player` (`scripts/build-chat-player.mjs`, esbuild) bundles `chat-player/` (which imports the app's own rules: `lib/core/exercises.ts`, `components/exercises/player-state.ts`) into the player's two pages and the review page, and writes `lib/mcp/chat-player-html.ts` (`CHAT_PLAYER_HTML`, `CHAT_PLAYER_ARTIFACT`, `CHAT_REVIEW_HTML`), which is committed like `public/lexique/*`, so the connector serves it with no build step. The script refuses a bundle that contains `</script` or a template without exactly one slot. Rebuild after changing `chat-player/` or the rules it imports.

#### «Мини-TCF» (`play_exercises` `mode: "exam"`)

The exam mode of the same player (`chat-player/exam.ts` rules, `exam-ui.ts` screens; SPEC.md «Чат-приложения», Мини-TCF A). Asked for «мини-TCF», «как на экзамене» or «пробный TCF», Claude writes about 12 items from A2 to B2, each with its `level`, about half `reading`, and sends them with `mode: "exam"`.
- **Start card:** «МИНИ-TCF · 12 ВОПРОСОВ · 18 МИН», the title, the levels strip from the items' levels, «Состав» by type («6 текстов · 4 значения · 2 пропуска»), three rules, «Начать 18:00».
- **Questions:** the set's order, each once (pairs boards are left out: nothing to pick A–D; a set with only pairs falls back to practice). Header «07 / 12 · МИНИ-TCF · ТЕКСТ» with the countdown on the right (red under 2:00) and a progress line; options as A–D rows; a pick, then «Ответить». No stamp, no feedback, no requeue, no «Не знаю», no going back.

- **Model context:** at the end and after saving, one line (score, time, by level, each mistake). Saving is `save_exercise_result` with `saveArguments`, exactly as a practice round (`mode` and `time_limit_s` are not sent); the saved set plays in the app as a practice round.

## Rotating or revoking

1. Generate a new secret and set it as `MCP_SECRET` in Vercel, then redeploy. The old URL starts answering 404 immediately.
2. In claude.ai, remove the connector and add it again with the new URL. A connector's URL can't be edited in place.

To switch the connector off entirely, delete `MCP_SECRET`, or `SUPABASE_SECRET_KEY`, and redeploy.

## Limitations and trade-offs

- **Anyone with the URL has full read and write access to the words.** There is no second factor. Treat the URL like a password.
- The URL can end up in browser history, in screenshots of the connector settings, and in Vercel's request logs (they record paths). Rotate the secret if it may have leaked.
- The secret key bypasses RLS. The `user_id` filters in `lib/mcp/repo.ts` are what keep the connector to one account; keep every query in that file.
- Claude sees the synced copy only. Words added on a phone that hasn't synced yet are invisible, so a duplicate check can miss them.
- Last-write-wins is per row. If the phone edits a word offline while Claude edits it too, one of the two edits is lost when they meet; Claude is told when its own write lost.
- Two `add_words` calls running in parallel can both pass the duplicate check. The server instructions tell Claude to make write calls one at a time.
- The rate limit lives in one serverless instance's memory: it stops a runaway loop, not a determined caller.
